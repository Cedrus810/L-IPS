# LCWLD-090/100 设计说明：加速到底从哪来

- 日期：2026-09-03
- 前置：LCWLD-050 完成；DEC-004（fp32）、DEC-005（验收阈值）冻结
- 状态：**设计，代码未写**

## 1. 一句话

`CustomGBForce` 对 dens、pair、chain 三件事**都遍历完整的 rc 邻居表**；但 dens 和 chain
的支撑半径其实只有 `r_env`。融合 kernel 只在 pair 上付全 rc 的代价。

```
r_env = 0.35 nm,  rc = 1.2 nm
体积比 (r_env/rc)³ = 0.0248  →  密度相关的遍历只碰 2.5% 的 pair
```

| | 遍历结构 | 相对代价 |
|---|---|---:|
| `CustomGBForce`（通用） | 3 趟全 rc（computedValue / energy / chain rule） | 3.00 |
| 融合 kernel | 1 趟全 rc（pair）+ 2 趟 r_env（dens、chain） | 1.05 |

`f = 1.05 / 3.00 = 0.35`，即 kernel 本身快约 **2.86 倍**。代入
`overall = 1/((1−s) + s·f)`，**1AAY 实测 s = 0.845**：

    overall = 1/((1−0.845) + 0.845×0.350) = **2.22×**      48.4 GPU 小时 → 21.8 h

⚠ 这个数我先后写错两次（2.12× 是用 s=0.811 算的旧值；2.36× 是算术错）。公式写在上面，
以后改 s 直接重算，别再手推。

这落在 DEC-005 立项预期的 2–3× 内，而且**这个 f 有结构依据**——它来自两个半径的体积比，
不是估的。这也解释了为什么 `CustomGBForce` 慢：它慢在**遍历结构**和通用表达式求值吃
寄存器，不在于没被编译。它本来就是 OpenMM 生成并编译的 CUDA kernel。

### 定案（2026-09-03，双系统 rc 扫描）

前面几轮的模型推演全部作废，以下是实测。`force_cost --rc-scan 0.35,0.5,0.7,0.9,1.2`
同时扫完整系统和去掉 CustomGBForce 的对照系统，相减得到 CustomGBForce 自己的成本：

    rc      完整 ns/day   CustomGB 成本   其余力成本
    0.35       323.56        0.109         0.084
    0.50       226.25        0.193         0.083
    0.70       151.77        0.318         0.093
    0.90       101.23        0.501         0.116
    1.20        62.46        0.846         0.154

**关键量是直接测出来的，不用任何模型**：rc=0.35 正好是 r_env。

    r_env/rc 成本比 = 0.109/0.846 = **0.129**
    f = (1 + 2×0.129)/3 = **0.419**
    s = 0.846（rc=1.2 处原始测量；与 --speed 那次的 0.845 独立吻合）
    端到端 = 1/((1−0.846) + 0.846×0.419) = **1.97×**    48.4 h → 24.6 h

**口径：`f ≤ 0.419`，端到端 `≥ 1.97×`。** 这个 0.129 是**用 tile 遍历**测的，
tile 粒度地板还在；本设计用紧凑 flat 列表，没有 tile 粒度，只会更好。
（反方向风险：flat 列表访存合并比 tile 差，未必吃到全部差额。）

三个来源对比，实测落在两个推演之间：

| r_env 成本比 | 来源 | f | 端到端 |
|---:|---|---:|---:|
| 0.025 | 设计假设（纯体积比） | 0.350 | 2.22× ← 偏乐观 |
| **0.129** | **实测** | **0.419** | **1.97×** |
| 0.190 | 模型 2 外推 | 0.460 | 1.84× ← 偏悲观 |

### 成本模型：扫到 0.35 之后只剩一个活的

| 模型 | 最大残差 | 参数 |
|---|---:|---|
| `fixed + trav·rc³` | **47.9%** | 死。窄区间上的假象 |
| `a·(rc+d)³` | 12.0% | d=0.584 |
| `a·rc^p` | 10.1% | p=1.744 |
| **`a·(rc+d)³ + c`** | **2.3%** | a=0.108, **d=0.842**, c=−0.072 |

`d = 0.842 nm` 正是 **32 原子 block 的有效直径**：1AAY 密度 95.6 原子/nm³ ⇒ 一个 block
占 0.335 nm³ ⇒ 边长 0.694、体对角 1.203 nm，0.842 落在其间。**tile 粒度地板是真的**，
它在 rc 0.6–1.2 的窄区间里被"固定开销"这个假象吃掉了，扫到 0.35 才露出来。

⚠ 之前那个"固定开销 27.5%"是在**总步时**上、**窄区间**里拟合的，混进了其余力自己的
开销（实测 0.080）。分离后 CustomGB 自己的 fixed 只有 0.143。双系统扫描就是为解决
这个而加的。

### 结论

* 立项预期 **≥ 2.0×**（保守写 1.97×），落在 2–3× 下沿
* DEC-005 未达标线 1.5×，**余量 0.47×** —— 那个"要不要重定阈值"的待决项**自动消解**，
  不需要动它。按"结果出来前才算数"的规则，现在也正好还没测 kernel 跑分
* 天花板仍是 **2.32–3.63×**（本设计不删固定开销），**不是 6.47×**

## 2. 计算图## 2. 计算图

```
        ┌── pass A（r_env）──┐
源原子 ─┤ dens_i = Σ_j w(r) ·│─→ dens
        │ src_j · sink_i     │
        └────────────────────┘
                 ↓  逐粒子，无邻居遍历
        Q_i = qbase_i + clamp(dpolar_i · tanh(k·dens_i/rho0))
        dQ_i/ddens_i
                 ↓
        ┌── pass B（rc）─────────────────────────┐
        │ U   += k·[Δ_ij/r + q_iq_j·P(r) + …]    │  pair energy
        │ F   += 直接力                           │
        │ λ_i += k·Σ_j q_j·closure(r)            │  伴随量
        └────────────────────────────────────────┘
                 ↓
        ┌── pass C（r_env）──────────────────────┐
        │ F += λ_i·(dQ_i/ddens_i)·(ddens_i/dr)   │  链式力
        └────────────────────────────────────────┘
```

pass A 和 pass C 遍历同一组 r_env 边。**可以合并成一趟**（A 时缓存边、C 时复用），
若寄存器/共享内存放得下——那会把 1.05 压到 1.025，f→0.342。先按两趟实现，
融合作为 LCWLD-150 的优化项，不在正确性阶段做。

## 3. 精度

全 fp32（DEC-004）。已实测确认（DEC-005 §3.3）：OpenMM CUDA 用 **64 位定点累加**力和
能量，所以 scatter-add 的次序噪声远低于纯 fp32 分析给出的量，`single` 与 `mixed` 在
**力的计算上逐位相同**。逐粒子累加沿用平台的定点缓冲，不要自己写 fp32 归约。

## 4. 正确性怎么验（DEC-005 全文，这里只列关口）

- Oracle：**真实 1AAY 上的生产 CustomGBForce**，GPU 对 GPU。
- **逐粒子**比，对照集 A（12 真配位）/ B（`HIE149:ND1` 单列）/ C（3 个 Zn）/
  D（各 200 水 O、H）/ E（全体分位数）。
- 力阈值 **atol 1.0 kJ/mol/nm**（噪声地板 ×8.2，最弱真信号的 1/106），rtol 2.5e-4 并列取宽。
- **强制断言**：`HIE149:ND1` 的 ΔF 必须仍 < 1 kJ/mol/nm。它 dens≈0（距 Zn 13.13 Å），
  按设计就该没有响应；变大即说明 dens 算错。这是统计判据天然测不到的那一侧。
- cutoff 归属翻转（约 29 kJ/mol/nm 的离散跳变）单独立规则，不混进统计阈值。
- `localcwld_reference`（float64）保留为**定位** oracle：对不上时用来区分故障在
  host 层 / device kernel / metadata 映射。不进 `lips`、不进报告论证链。

## 4b. OpenMM tiled 邻居表的确切布局

从 OpenMM 源码 commit `36a30cb`（**正是本机这份 OpenMM 编译用的 commit**）挖出来的，
装在 conda 里的头文件不含这些。记在这里免得再挖一次：

`platforms/cuda/src/CudaNonbondedUtilities.cpp`：

```cpp
maxTiles = 20*numAtomBlocks;                 // 上限，可能被动态扩到 1.2*实际
interactingTiles.initialize<int>(context, maxTiles, ...);
interactingAtoms.initialize<int>(context, TileSize*maxTiles, ...);
```

`platforms/common/src/kernels/customGBValueN2.cc` 的遍历骨架：

```c
unsigned int numTiles = interactionCount[0];
if (numTiles > maxTiles)
    return;                                  // 邻居表溢出，本步放弃（OpenMM 会重建）

x = tiles[pos];                              // interactingTiles[pos] = x 块号
unsigned int atom1 = x*TILE_SIZE + tgx;      // x 侧 32 个原子，tgx = warp 内 lane
unsigned int j = interactingAtoms[pos*TILE_SIZE + tgx];   // y 侧 32 个原子
// 之后是 tile 内 32x32 全对，用 warp shuffle 轮转 y 侧
```

**两个循环，不是一个**：
1. 先遍历 `exclusionTiles`（含排除对的 tile），用 `exclusions[]` 位掩码逐位屏蔽；
2. 再遍历邻居表里的 tile，并**跳过**已在第 1 步处理过的那些
   （`skipTiles` 那段就是干这个的）。

漏掉第 1 步的后果不是"少算一点"——含排除对的 tile 里**所有**pair 都会缺失，
包括不该被排除的那些。这类错误表现为小的力误差，看起来像精度噪声。

### 对我们的取舍

`buildEnvPairs` 每次邻居表重建才跑一次，**不需要 warp shuffle 那套性能写法**：
一个 warp 处理一个 tile、每 lane 持一个 x 原子、串行扫 32 个 y 原子即可，正确且简单。
`computePairAndAdjoint` 是每步都跑的热路径，先按同样的简单写法保证正确，
warp 级优化留给 LCWLD-150——**在 DEC-005 的逐粒子对照通过之前不做任何优化**。

## 6. 立项前提：s 已满足，但成本模型前提未通过

**1AAY 的 `s` 实测 = 0.845**（2026-09-03，完整 CWLD 63.06 vs 去掉 CustomGBForce
407.83 ns/day）。这一条满足了。

但**第二个前提（成本 ∝ rc³）实测不成立**，见第 1 节：指数 1.52，固定开销 27.2%。
端到端从 2.22× 降到 **1.59–1.89×**，本设计的天花板从 6.47× 降到 **2.32–3.63×**。
**立项书上的 2–3× 不再成立**，在区间收紧之前不要引用它。

两条随之而来的约束，写进立项书：

1. **即使 kernel 免费也追不平 PME**：上界 407.83 ns/day vs PME 约 663，仍慢 1.63×。
   原因是 cutoff 不同（PME 1.0 nm，CWLD 的 NonbondedForce 用 rc 1.2 nm，
   直空间 pair 多 1.73×），与 CWLD 机制无关。
2. **瓶颈会转移**：rc=1.2 nm 的 NonbondedForce 现在占 15.5%，kernel 快 5× 后涨到约 48%。
   实测整体若只有 2× 左右，先查瓶颈是否已转移，再怀疑 kernel。现在动它不值得。

## 7. LCWLD-150 实测（2026-09-04）：成本模型漏了两项

同 binary 三臂，1AAY 32794 原子，RTX 2080 Ti，CUDA mixed，warmup 1000 / measure 4000。

    轮次                        f        端到端     说明
    初版（每 pair 一线程）    1.4232     0.736x    比 CustomGBForce 还慢
    warp-tile 重写            1.0761     0.939x    原子操作 6144->256/tile
    修发射几何                0.5984     1.518x    8192 -> 69632 线程

**当前状态：未达标。** 端到端 1.518x 对 DEC-005 第 5 节的 1.5x 未达标线只高 **1.2%**，
而同配置生产日志的运行间散度就有 1.5%（T1–T4 CWLD 58.4/58.6/59.0/59.3 ns/day）。
**单次测量不足以判 PASS**，需三臂各 3 次报均值±散度。阈值不能事后改（第 6 节），
所以判定必须有统计意义，否则一次抽样就把结论定了。

### 已定位的两条原因

1. **发射几何硬编码**（已改，已复测）。pair kernel 发 64 blocks × 128 threads = 8192。
   设备 68 个 SM，64 个 block 铺不满，每 SM 4 warp（上限 32），占用率约 12.5%。
   OpenMM 自己跑同一种 tile 遍历用 `4×68 = 272` blocks × 256 = 69632。
   改为从 `NonbondedUtilities::getNumForceThreadBlocks/getForceThreadBlockSize` 取。
   `energyBuffer` 尺寸保证见 `CudaContext.cpp:400` + `CudaNonbondedUtilities.h:124`。
2. **每步一次阻塞 device→host 读**（未改）。`needsEnvRebuild()` 读 4 字节重建标志。
   OpenMM 读同一个标志是在 device 上、kernel 内部读的。代价未量，探针 B 是它的上界。

### 成本模型：第 1 节的 f = 0.419 漏了两项

单位 = 一趟完整 rc tile 遍历。实测重建间隔 = 1210 次 / 5000 次受力计算 = **4.13 步**
（`new` 臂不做极小化，所以受力次数就是 warmup+measure）。

    项                                      第 1 节    实际
    pair 遍历（完整 rc）                     1.000     1.000
    buildEnvPairs（完整 rc，1/4.13 摊销）      —       0.242   ← 漏项 A
    density + chain（2 × 0.129 × 2.13）      0.258     0.549   ← 漏项 B
                                            ─────     ─────
                                       f =  0.419     0.597
                                       实测           0.598

* **漏项 A**：设计写"1 趟全 rc + 2 趟 r_env"，但**建紧凑表本身就是一趟完整 rc 遍历**。
  它只能摊销到 OpenMM 的重建计划上（4.13 步），不能更少 —— 我们读的就是它的标志。
* **漏项 B**：`paddedEnv = r_env + 0.1 = 0.45 nm`，而 0.129 那个比值是在 **0.35** 上测的。
  `(0.45/0.35)³ = 2.13`。这同时解释了当初"容量按体积比估 208340、实际 >2 倍"——
  304528 就是 0.45 nm 表的长度。
  padding **不可调**：OpenMM 的重建判据是任一原子位移 > padding/2，两次重建间一对原子
  最多靠近 0.1 nm，所以 0.1 是正确性下界；调大也不减重建次数（我们跟它的标志走），
  只会更贵。**当前值恰好最优。**

三项模型与实测差 0.3%。这个吻合度在三项模型上多半有运气成分，**用探针 A 证伪**：
r_env 压到 1e-4 时模型预测 f_A ≈ 0.414（padded 表退化到 0.1 nm，pair 数约 1%）。

### 如果模型成立，剩下的空间在哪

density+chain 占 0.549 / 0.598，**超过一半**。第 2 节末尾已经写过它们遍历同一组边、
可以合并成一趟，当时列为 LCWLD-150 优化项。合并后：

    f = (1 + 0.242 + 0.274)/3 = 0.505    端到端 = 1.73x

### 漏项 A 也可以压掉：建表挂进已有的那趟遍历

上面写"buildEnvPairs 只能摊销到 4.13 步，压不掉"。那句只对了一半。**压不掉的是重建
频率，不是那趟遍历本身** —— 因为每一步本来就已经有一趟完整 rc 遍历了：pair pass。
重建步上两者遍历的是**同一组 rc pair**。跟"density 和 chain 遍历同一组边、可以合并"
是同一个道理。

⚠ **挂载点只能是 `computePairAndAdjoint`。** `computeChainForce` 走的是紧凑表
（它的参数里只有 `envPairs`/`envPairCount`，没有 `tiles`/`interactingAtoms`），
从它身上生不出 rc 表。每步唯一的另一趟完整 rc 遍历就是 pair pass。

次序上没有冲突，而且"下一步才用"是**必需的**而非将就：density 在 pair 之前跑，
所以重建步上当步本来就用不到新表。pair pass 产出的表从下一步开始用。
正确性代价是从 padding 预算里再扣一步的漂移（一步最大位移约 0.004 nm，
对 0.1 nm 预算是 4%）；把重建阈值从 `pad/2` 收到 `pad/2 − 一步最大位移` 即完全守住。

    路线                              f       端到端
    现状                            0.597    1.52x
    只做 density+chain 合并          0.505    1.73x
    只把建表融进 pair pass           0.533    1.66x
    **两者都做**                     0.441    **1.90x**

**所以第 1 节那个 1.97x 是用漏了两项的模型算出来的，够不到；但"现实目标 1.73x"
也偏保守。** 两项优化都做完，模型给 **约 1.9x**。真正压不掉的只剩 padding 那
`(0.45/0.35)³ = 2.13` —— 它是正确性要求。

⚠ 1.90x 与上表其余各行**同样来自模型**，且这个模型只在一个点上对过（0.3%，有运气成分）。
**实测之前不要引用任何一行。** 探针 A 是第一道检验。

### padding 已定量确认在最优点

把 padding 当自由参数扫（间隔 ∝ pad，判据是位移 > pad/2；表长 ∝ (0.35+pad)³；
建表成本恒为一趟全 rc，与 pad 无关）：

    pad    间隔    f       端到端
    0.050  2.06   0.623   1.47x
    0.075  3.10   0.595   1.53x
    0.100  4.13   0.597   1.52x   ← 当前
    0.125  5.16   0.613   1.49x
    0.200  8.26   0.707   1.33x

最优区间宽而平，落在 0.075–0.10，**当前的 0.1 就在最优点上**，两个方向都变差。
这条不需要实验。（注：建表融进 pair pass 之后这张表要重算 —— 建表成本掉到约 0.05，
最优点会往大 padding 方向移。）

### 复现口径

三次复测必须**串行、单独占 GPU**。生产日志那 1.5% 散度本身含并发成分
（T1–T4 是并发跑的，另有 38.9/39.0 两档更低的是被抢占的）。并发下散度偏大，判定更不稳。

## 8. 探针 A/B 实测（2026-09-04）：第 7 节的模型被证伪

    配置                                   f        端到端    总成本（rc 遍历当量）
    基线                                 0.5984    1.518x        1.795
    探针 A（r_env=1e-4，density+chain≈0） 0.5719    1.572x        1.716
    探针 B（每步重建，无同步）             0.7761    1.235x        2.328

### 第 7 节错在哪

    density + chain = 1.795 − 1.716 = 0.079      模型说 0.549，错 7 倍

原因：0.129 那个成本比是在 **tiled** rc=0.35 遍历上测的，而第 1 节自己就查明那里面
含 **tile 粒度地板**（`a(rc+d)³+c` 拟合出 d=0.842 nm = 32 原子 block 的有效直径）。
紧凑 flat 列表**没有 tile 粒度**——第 1 节原话"本设计用紧凑 flat 列表，没有 tile 粒度，
只会更好"是对的，是第 7 节的模型把这句丢了，拿含地板的数去估无地板的结构。

**推论：density + chain 合并不值得做。** 它俩合计只占 4.4%。第 7 节把它列为首选优化，
那条建议作废。

### 探针 B 给的是约束线，不是数值

它同时改了两件事（重建频率 1/4.13→1，同步 S→0）：

    2.328 = 1.795 − B/4.13 + B − S    ⇒    0.7579·B − S = 0.533

`B` = 一趟 buildEnvPairs 的成本，`S` = 每步同步的成本。`S ≥ 0` ⇒ **`B ≥ 0.703`**。
代入 `P = 2.249 − B`（P = pair pass 成本）：

    B=1.00 ⇒ P=1.249, S=0.225        两个待选优化的价值差一个量级，
    B=0.80 ⇒ P=1.449, S=0.073        所以必须分开 —— 见探针 C
    B=0.70 ⇒ P=1.546, S=0

### 真正的大头：pair pass，占 70–86%

无论 B/S 怎么分，pair pass 都是 **1.25–1.55 个遍历当量**。但这**多半不是 bug**：

第 1 节把 CustomGBForce 记为"3 趟"，隐含**三趟等价**。它们不等价 —— value 趟只算 dens
很便宜，energy 趟和 chain-rule 趟贵。而**我们的 pair pass 一趟里做了 energy + chain-rule
两趟的算术**。所以"三趟合一趟省 3 倍"从来不成立：省下的是**一趟的访存**，
不是一趟的总成本。1.25–1.55 正是"一趟遍历 + 两趟算术"该有的量级。

算术核本身没有可挖的：`RSQRT` + Horner，无除法、无超越函数、约 20 flop
（`LOCALCWLD_PAIR_CORE`，`localCWLD.cc:86`）。

### 现在的口径

**上一轮那张 1.73x / 1.90x / 1.94x 的外推表全部作废** —— 它建立在 density+chain 占
0.549 这个已被证伪的前提上。**在探针 C 之前不给新目标。**

顺带修掉一处与 DEC-004 冲突的实现：`fixedPointToReal` 原本在 device 上做 **fp64 除法**
（`(double)x / 0x100000000`），消费卡 fp64 吞吐是 fp32 的 1/32。改为乘 `(real)0x1p-32`
（2 的幂，精确）。验收数字逐项不变（p99 4.351e-03）。它只出现在 `computeQ`（逐原子）
和 `computeChainForce`（占 4.4% 的桶里），**不在热路径**，所以这是合规修复，不是性能修复。

## 9. 归因闭合（2026-09-04 晚）：第 8 节的结论有两条是错的

第 8 节用探针 A + B 解 B/S，两个未知数一个方程，还漏了重建块里的三次阻塞传输。
探针 C（建一次表后永不重建、**保留**每步同步）补上第三个方程，方程闭合。

三个配置都用**轮转协议**测（三臂交替、3 轮取中位数，轮间比值散度 1.2–2.9%）：

    配置                                  f       端到端
    基线                                0.6045    1.514x
    探针 C（永不重建，保留同步）           0.5168    1.713x
    探针 B（每步重建，跳过同步）           0.7802    1.233x

    基线   = P + D + T/n + S        n = 1210/5000 的倒数 = 4.13 步
    探针 C = P + D +  0  + S
    探针 B = P + D +  T  + 0

解得（f 单位，CustomGBForce ≡ 1）：

    项                     f 单位    占比     rc 遍历当量
    P   pair 遍历          0.3913   64.7%      1.174
    S   每步阻塞同步        0.0990   16.4%      0.297
    T/n 建表（摊销后）      0.0877   14.5%      0.263
    D   density+chain     0.0265    4.4%      0.080
                          ------   ------
                          0.6045  100.0%

    单次重建事件 T = 0.3624 f 单位 = 1.087 个 rc 遍历当量
    （一趟遍历 + 一次 upload + 两次阻塞 download，所以超过 1.0 是合理的）

### 更正 1：pair pass 是 1.174 当量，不是 1.25–1.55

第 8 节写"pair pass 占 70–86%"，实测 **64.7%**，且只比设计假设的 `1/3` 高 **17%**。
那个区间是从探针 B 的错误解读里推出来的（解出的 S 是负数，那本该当场作废）。

### 更正 2：`f = 0.419` 可达，第 8 节说"从来不可达"是错的

    路线                                    f       端到端
    现状                                 0.6045    1.514x
    只把标志判断挪进 kernel（去掉 S）      0.5055    1.738x
    + 建表融进 pair pass（残余取 25%）     0.4397    1.927x
    （下界）建表完全免费                   0.4178    1.999x
    设计目标                              0.4190    1.995x

**下界 1.999x 与设计目标 1.995x 重合。** pair pass 超出的那 17% 完全落在设计自身的
余量里 —— 第 8 节"三趟不等价所以够不到"的推断，前提数据本身是错的。

⚠ 1.738x 是"从实测里减掉一项"，比较硬；1.927x 里的"残余 25%"是**猜的**，
建表融合之后必须重测。

### 不变的结论

**density + chain 合并仍然不值得做**（4.4%）。第 7 节把它列为首选优化那条依旧作废。

### 待办与口径

1. **把标志判断挪进 `buildEnvPairs`**（`envPairCount` 的清零挪进 `clearBuffers` 做
   条件清零）。收益 0.0990 f 单位 ⇒ 端到端 1.514x → **1.738x**。
2. **建表融进 `computePairAndAdjoint`**（唯一的另一趟完整 rc 遍历；chain 走的是紧凑表，
   挂不上去）。次序：pair pass 产出、下一步开始用 —— density 在 pair 之前跑，
   所以重建步当步本来就用不到新表。收益上界 0.0877 f 单位 ⇒ **约 1.93x**。
   ⚠ 这一步会往热路径塞写出动作，可能把 P 自己变慢，净收益必须实测。
3. ⚠ **`D` 仍带一个协议错配**：探针 A 是在旧的"三臂串行各测一次"协议下跑的
   （基线 0.5984 对新协议的 0.6045，差 1%），误差被 `P` 吸收。重构前值得用轮转协议
   重跑一次探针 A，把 `D` 和 `P` 收紧。

### 测量协议：热降频，锁不了频

这张 2080 Ti 降频很凶且**没有锁频权限**（`nvidia-smi -lgc` 报无权限）。
三臂各 4000 步连跑 3 轮，绝对速率单调掉 **12.7%**；5 轮掉 **23.4%**
（gb 57.95 → 46.96 ns/day，SM 时钟 2175 上限 → 1350）。

**但轮转让比值免疫**：同一轮内三臂在几乎相同的热状态下被测。

    绝对速率散度 12.7%    →    端到端比值散度 0.23%

所以判定闸门必须门**比值**的散度，不是速率的散度 —— 初版门错了对象，
把一次比值稳到 0.23% 的运行判成了"机器不干净"。

⚠ 轮转只消一阶。**轮内顺序仍有系统偏差**（先跑的臂时钟更高），5 轮那次比值散度就涨到
2.7%。彻底的做法是隔轮反转臂序；已实现但未启用（用户裁决：不折腾频率）。
**推论：跑 3 轮，别跑 5 轮** —— 长跑并不会让这个测量更准，只会更热。

## 10. 单变量重测（2026-09-04 深夜）：第 9 节的四项分解是过度拟合

第 9 节用三个探针解四个未知数，得出"同步占 16.4%、去掉后 1.738x、下界 1.999x 与设计

差在哪：**每个探针都改了不止一件事**，而且三次运行之间有热漂。直接把同步加回来测
（`LOCALCWLD_PROBE_SYNC=1`，只改这一件事）：

    f 0.5839（无同步）  vs  0.5896（有同步）   ⇒  一次每步阻塞读 = 0.006 f 单位

**不是 0.099。模型推高了 17 倍。** 三点模型作废。

把重建判断从 host 挪到 device（`buildEnvPairs` 读 `rebuildFlag` 后立即返回），
`envPairCount` 的清零挪进 `clearBuffers` 条件执行，容量检查从"每次重建"降为
"前 8 次求值 + 之后每 100 次"，且**溢出改为抛错而不是静默扩容**。
f 0.6045 → 0.5839，端到端 1.514x → **1.559x**。收益比预测小得多，但方向对，且
去掉了一整类每步同步。

## 11. 理论天花板：用"一趟普通 rc 遍历"当单位

前面所有的 f 都以 CustomGBForce 为 1，那是个**坏单位** —— 它是三趟不等价的 pass 的总和，
所以"我们是 0.58"既不说明快也不说明慢。换一个有物理意义的单位。

`ARM_BARE`（同时去掉 CustomGBForce 和 NonbondedForce）把它量了出来。
体系里的 `NonbondedForce` 是 **CutoffPeriodic、同一个 1.2 nm、同一张邻居表**
（`method=2`，见 dump），也就是**一趟纯粹的 rc 遍历**，而且是 OpenMM 优化得最狠的 kernel 之一。

    一趟普通 rc 遍历        = 0.1305 个 CustomGBForce
    CustomGBForce 本身      = 7.7 趟（三趟 pass，平均每趟 2.6 趟）
                              ← 通用表达式求值的代价，设计第 1 节猜到了这一点
    **CWLD 力（当前）       = 4.49 趟**

### 天花板

CWLD 的物理是**一次 rc 上的逐对相互作用**（`1/r` + ZMM 闭合多项式），外加一个
实测成本约等于零的局域密度项。所以它的地板应该在 **1 趟**附近 —— 比
`NonbondedForce` 多的只有：ZMM 多项式（几个 FMA）、伴随量累加（每原子每 tile 多一次
原子操作）、以及三个额外的逐原子数组读取。给到 1.5 趟是宽松的。

    情形                                    f       端到端
    现状（4.49 趟）                       0.586    1.55x
    融合建表（实测天花板，探针 C）           0.519    1.70x
    pair pass 降到 2.0 趟                 0.261    2.72x
    降到 1.5 趟  ← 现实目标                0.196    3.21x
    降到 1.0 趟（与 NonbondedForce 同价）   0.131    3.91x
    力完全免费（Amdahl 绝对上限）            0        6.93x

**结论：剩下的性能全部在 pair kernel 里。** 它现在是 4.49 趟，物理只要 1–1.5 趟。
把建表融进去只值 0.15x，而把 pair pass 从 4.5 趟做到 1.5 趟值 **1.55x → 3.2x**。

⚠ 3.2x 是**目标不是预测**。4.49 → 1.5 需要找出那 3 趟的开销在哪，而那还没查。
已知的嫌疑（未验证，按优先级）：

1. **LOCAL 内存占用**：pair kernel 用了 5 个 LOCAL 数组
   （`localPos/localQ/localQbase/localForce/localAdjoint`），256 线程/块下约 10 KB，
   而 OpenMM 的非键 kernel 少得多。可能限制了占用率。
2. **每原子每 tile 多一次原子操作**（伴随量），非键只有力。
3. **多读三个逐原子数组**：非键把电荷打包进 `posq`，我们额外读 Q、qbase，还要写 adjoint。
4. **寄存器压力**：算术核 + 5 个 LOCAL 缓冲，可能已经溢出到 local memory。

下一步应该是 `ncu` 看占用率、访存吞吐和 stall 原因，**而不是继续猜**。
这一节所有的数都来自单变量实测；上面那四条嫌疑一条都没有。
