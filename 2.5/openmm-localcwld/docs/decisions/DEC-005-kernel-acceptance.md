## 为什么现在写

**先写 kernel 再定阈值，阈值一定会被拟合到跑出来的偏差上。** 那时候"通过"只意味着
"阈值是照着结果画的"。所以这份文件在 device kernel 一行代码都还没有的时候落盘。

计划第 9/25 节那份阈值表是按 **double 精度 Reference** 写的，对一个 fp32 GPU kernel
（DEC-004）不适用，作废。以下取代它。

## 1. Oracle 是谁

**生产 `CustomGBForce`，在真实 1AAY 体系上，GPU 对 GPU。**

不是 CPU Reference。用户 2026-09-03 明确"`localcwld_reference` 纯纯看数值准不准的，
也不是我们需要的"，而且 GPU-vs-GPU 才是要验的那件事：新 kernel 必须复现**生产里
真实在跑的那个东西**，包括它的 fp32 舍入。

但 `localcwld_reference`（Python, float64）**保留在插件内部作为定位 oracle**，不进
`lips`、不进任何报告的论证链。理由是纯工程的：新 kernel 与 CustomGBForce 对不上时，
故障可能在 (a) common host 层、(b) device kernel、(c) metadata 映射 三处；只有一个
GPU-vs-GPU 对照点无法把三者分开，只能整栈二分。第三个点是用来定位的，不是用来判对错的。

LCWLD-030 的 7 个 golden fixture 继续作为小体系回归（分支覆盖），不作为验收依据。

## 2. 必须逐粒子比，不许比总量

32794 个原子里 13 个偏 3%，看总能量/总力**根本看不出来**。

验收对照集必须显式包含：

| 组 | 内容 | 为什么 |
|---|---|---|
| A | 13 个 `LIGAND_DPOLAR_OVERRIDE` 命中原子 | 报告主结论的归因落点 |
| B | **`HIE149:ND1` 单独一行**，不并进 A 的统计 | 距最近 Zn **13.13 Å**，是唯一"覆盖生效但环境是体相"的原子。它的 `dens` 应显著低于另外 12 个——**天然的假阳性探针**：若它的 dens 跟配位原子相当，说明 dens 算错了 |
| C | 3 个 Zn²⁺ | 金属本身 |
| D | 随机 200 个水 O + 200 个水 H | 占体系绝大多数，抓系统性偏差 |
| E | 全体 32794 原子的分位数（p50 / p99 / max） | 抓尾部 |

分级报偏差，不要只报最终力：`dens` → `Q` → `energy` → `force`。偏差在哪一级出现直接

## 3. 阈值 —— **必须先做零点实验测出来，不许拍脑袋**

### 3.1 为什么本节原来的数字被作废

本文件初稿直接给了一张阈值表（dens/Q rtol=1e-4、力 rtol=2e-4、**总能量 rtol=1e-5**）。
peer `2-5-9c` 指出它有两个致命问题，已核实成立：

1. **总能量 1e-5 在 fp32 下做不到，是一颗必炸的地雷。** 它比力的阈值还紧 20 倍，方向
   反了。总能量是海量项求和，fp32 误差按 √N·ε 累积：CWLD 的 pair 数量级约 1e7
   （32794 原子 × rc 内每原子几百个邻居），`√1e7 × 6e-8 ≈ 2e-4` 相对——已经超出原阈值
   一个量级以上，还没算静电正负相消（总量小、分项大）带来的进一步恶化。
   交付时这一栏必然红，而本文件第 6 节又写死"不得事后改阈值"，唯一出路变成推翻决策
   文件本身——正是那条规则想避免的局面。

2. **两个对照对象都是 fp32 GPU，没有一方是真值。** 新 kernel 和生产 CustomGBForce
   都跑 fp32 CUDA，光是**求和顺序不同**就能在 1e-4 量级产生差异，与 kernel 对错无关。
   所以那张表是**猜的**：猜紧了假失败，猜松了漏真 bug。

### 3.2 零点实验（写 kernel 之前做，结果直接定阈值）

同一帧、同一个 1AAY CWLD System，用**生产 CustomGBForce** 在三种精度下各取一次
`getState(getForces=True, getEnergy=True)`。纯静态，零 `Integrator.step()`。

| Precision | 角色 |
|---|---|
| `double` | 当近似真值 |
| `mixed`  | **生产轨迹实际用的**（`zn_job.py` 默认 `--precision mixed`，不是 single） |
| `single` | 新 kernel 按 DEC-004 要对齐的精度 |

它直接测出两件目前没人知道的事：

* **fp32 在这个体系上的固有噪声地板** —— 阈值取"实测地板的 3–5 倍"，有据可依，
  且因为在写 kernel 之前定死，不可能被事后拟合到结果上。
* **mixed 与 single 的差距** —— 生产数据跑的是 mixed，DEC-004 要求 kernel 走 single，
  两者差多少至今无人测过。若差距显著，DEC-004 的选择需要重新讨论。

**按分位数报（p50 / p99 / max），不要只报 max。** 单个 cutoff 边界原子就能把 max 拉爆，
而那正是第 4 节单独立规则处理的那一类。

脚本：`docs/reports/dec005_precision_floor.py`，结果落盘到
`docs/reports/dec005_precision_floor.json`。**必须落盘**——§4.1 那两个 Δq 就是毁在
没落盘上。

### 3.3 阈值（**已由零点实验填定，2026-09-03**）

零点实验已跑，两档配置各一次，产物落盘：
`docs/reports/dec005_precision_floor.json`（覆盖关）、
`..._dpolar.json`（`L_IPS_LIGAND_DPOLAR=-0.15 scope=metal`）。
真实 1AAY，32794 原子，同一帧同一 System，只改 `Precision`，零 `Integrator.step()`。

实测（两档结果几乎相同，说明地板与配置无关）：

| 对照 | rel_p50 | rel_p99 | rel_max | abs_p99 (kJ/mol/nm) |
|---|---:|---:|---:|---:|
| mixed vs double | 3.37e-06 | 5.52e-05 | 3.19e-04 | 0.122 |
| single vs double | 3.37e-06 | 5.52e-05 | 3.19e-04 | 0.122 |
| **single vs mixed** | **0** | **0** | **0** | **0** |

**发现 1：`single` 与 `mixed` 逐位相同。** OpenMM CUDA 的 `mixed` 只把积分器的
位置/速度存成 double，**力的计算与 single 完全一致**。所以 DEC-004 让 kernel 走
single，相对生产实际在跑的 mixed **没有任何数值代价**——这个悬着的问题就此关闭，
结论支持 DEC-004 原判。

**发现 2：能量的 fp32 误差远小于朴素估计。** 实测相对差
3.83e-06（覆盖关）/ 3.83e-06（覆盖开），而按 √N·ε（N≈1e7 pair）预估是 ~2e-4，
**乐观了约 50 倍**。原因是 OpenMM CUDA 用 **64 位定点累加**力与能量，求和顺序噪声远
低于纯 fp32 分析给出的量。3.1 节里"能量 1e-5 必炸"那个论证**在量级上是错的**——
但结论仍然保留：1e-5 只剩 2.6 倍余量太薄，而且新 kernel 与 CustomGBForce 是**不同算法**
（融合遍历、不同邻居次序），偏差会大于这里测到的纯精度地板。

| 量 | rtol | atol | 依据 |
|---|---:|---:|---|
| 逐粒子力 | **2.5e-04** | **0.5 kJ/mol/nm** | 地板 rel_p99 = 5.52e-05 × 4.5；atol 取 abs_p99 = 0.122 的 4 倍 |
| 总能量（粗筛） | **1e-04** | 30 kJ/mol | 地板 3.8e-06 × ~25，给算法差异留足余量；**不作为验收判据** |
| `dens` / `Q` | **待填** | 待填 | CustomGBForce 取不出中间量，等 LCWLD-100 能单独 dump 时按同法定 |

比初稿的猜测：力 rtol 2e-4 → **2.5e-4**（落在实测 1.66e-4~2.76e-4 带内，说明那个猜
其实不坏）；总能量 1e-5 → **1e-4 且降级为粗筛**。

A 组和 B 组（13 个覆盖原子 + `HIE149:ND1`）不适用统计阈值，逐个原子各自满足上表。
它们只有 14 个，没有"平均下来还行"这回事。

### 3.4 信号判据（**最终采用的那个**，2026-09-03）

peer `2-5-9c` 指出 3.3 的阈值是**对着噪声**定的：它只回答"同算法不同精度差多少"，
没回答"差多少才**算错**"。而新 kernel 是**不同算法**，偏差本来就该显著大于精度地板
——于是很可能 kernel 完全正确却判红，又只剩推翻决策文件一条路。跟总能量那颗地雷同源。

正确的判据对着**信号**定：`精度地板 ≤ 阈值 ≪ 要捕捉的物理效应`。

信号手上就有：把 override 关/开 两档在覆盖原子上的力作差，就是 `dpolar=-0.15` 带来的
力变化——正是把 PME 的 66.9% 顶到 100% 的那个东西。离线算，脚本
`docs/reports/dec005_signal_window.py`，结果 `..._signal_window.json`：

| | kJ/mol/nm |
|---|---:|
| 精度地板 abs_p99 | 0.122 |
| **12 个真配位原子 ΔF**：最小 / 中位 / 最大 | **106.4 / 197.4 / 254.0** |
| `HIE149:ND1`（体相探针）ΔF | **0.033** |
| 可用窗口 | **870×（2.9 个数量级）** |

**采用：逐粒子力 atol = 1.0 kJ/mol/nm**
= 精度地板的 8.2 倍（给"不同算法"留余量）
= 最弱真信号的 1/106（小到不足以改变任何结论）

正当性从"比噪声大 4.5 倍"变成"**小到不足以改变我们要测的结论**"——后者才是半年后
自己和审稿人都能接受的理由。rtol 2.5e-4 保留为并列判据，**取宽的那个**。

### 3.5 顺带：这次测量独立证实了 HIE149 的判定

`HIE149:ND1` 的 ΔF = **0.033**，比最弱真配位原子小 **3257 倍**。它命中化学判据、
dpolar 被覆盖成 −0.15，但因为距最近 Zn 13.13 Å、环境是体相，`dens≈0` ⇒
`tanh(k·dens/rho0)≈0` ⇒ `Δq≈0` ⇒ 力几乎不变。

三个独立结论：
1. 它确实不配位（几何判定之外的第二个独立证据）；
2. `dens → Δq` 这条链是**对的**——低 dens 就该没有响应，实测如此；
3. **100% vs 66.9% 的效应全部来自那 12 个真配位原子**，13 个里的第 13 个贡献为零。
   报告把标签从"13 个金属配位原子"改成"12 配位 + 1 远端"是对的，而且现在有力学证据。

**这条转为 LCWLD-120 的强制断言**：新 kernel 下 `HIE149:ND1` 的 ΔF 必须仍 < 1 kJ/mol/nm。
若它变大，说明 dens 算错了——这是一个比任何统计阈值都灵敏的单点探针。

### 3.6 ⚠ 这一节验的是 CustomGBForce，**不是** `_local_dens_at`

peer `2-5-9c` 标的界限，原样记在这里，因为它极易被下一个人读错：

3.2–3.5 的所有测量都出自**生产 `CustomGBForce`**。分析侧那份手抄镜像
`lips.engine.v26._local_dens_at` 与它**共用同一套数学，但不是同一份实现**。

具体后果：`REPORT_1AAY_ZN.md` §4.1 的三个 Δq 数字（0.1% / 0.75% / 11.5%）出自
`_local_dens_at`，而本文件的 ΔF 出自 CustomGBForce，**两者串不起来**。

所以本节的结果**不能顶替 A 工单**（`_local_dens_at` 对 CustomGBForce 的 parity）。
A 仍然是那份镜像唯一的验证途径，仍然待做。



### 3.7 偏置判据（幅度判据抓不到的那一侧，2026-09-03）

peer `2-5-9c` 指出 3.3–3.6 全是**幅度**判据（rtol / atol / 分位数 / HIE149 单点）。
而 tiled 邻居表最危险的错法——**漏 tile 或重复计 tile**——产生的是**单边偏置**：
dens 系统性偏低（漏）或偏高（重复），**符号恒定**。只要偏置小于 atol=1.0，四栏全绿，
物理却是错的。而且它恰好伪装成精度噪声。

区分办法很便宜：**精度噪声的符号是随机的，漏/重复 pair 的符号是恒定的**。所以除了
报 |Δ| 的分位数，再报带符号的均值和它的 t 值：

    mean(Δdens)                        dens 是标量，漏 pair 只会让它偏低
    mean(ΔF · F̂_ref)                   ΔF 在参考力方向上的带符号投影
    t = mean / (std / √N),  N = 32794

#### 基线是实测的，而且**不是零**

按 peer 的提醒先量了基线（纯精度噪声，single vs double，用已有的
`dec005_precision_floor.npz`，纯离线）：

| 量 | mean | t | 结论 |
|---|---:|---:|---|
| `ΔF·F̂_ref`（投影） | −4.53e-03 | **−5.57** | **显著偏离零** |
| ΔF 逐分量 x / y / z | ~0 | −0.00 / +0.00 / −0.00 | 与零相容 |
| \|F_single\| − \|F_double\| | −4.53e-03 | −5.57 | 单精度力系统性**偏小** |

51.4% 的原子单精度力偏小（纯随机应为 50.0%）。

**成因**：`realToFixedPoint` 里的 `(long long)` 强制转换是**向零截断**，不是舍入。
每次累加都略微偏小，符号恒定，于是力的幅度系统性偏低。这是 OpenMM 定点累加的固有
性质，不是 bug，但它意味着**天真的"t 落在 ±3 内"判据会让一个完全正确的 kernel 判红**。

#### ⚠ 作废：把 −5.57 当偏移量写进判据（peer 指出，已核实）

初稿写的是 `|t − (−5.57)| < 3`。**这是个盲区，而且正好对着最可能的 bug**：

1. **−5.57 是 fp32-vs-fp64 的偏置，不是 fp32-vs-fp32 的。** 上表测的是 single vs
   double——只有一侧有截断，偏置全额显现。而验收要比的是**新 kernel vs
   CustomGBForce，两侧都是 fp32**，两侧都向零截断 ⇒ 偏置大部分对消，真实基线接近 0。
2. 于是 `|t − (−5.57)| < 3` 等于在 `t ∈ [−8.57, −2.57]` 开了一个窗口。漏 pair 的
   kernel：dens 系统性偏低 ⇒ 力偏小 ⇒ **t 为负**，**正好落进这个窗口被放行**。
   为了防"正确 kernel 被判红"引入的偏移，恰好给最可能的那种 bug 让出了通道。
3. **而且真实偏移无法在 kernel 写出来之前确定**：截断偏置正比于定点转换的**次数**。
   融合 kernel 若在寄存器里用 float 累加、每原子只转一次，截断次数比 CustomGBForce
   少一两个数量级 ⇒ 偏置更小 ⇒ t 会是**正的**。这个量随实现设计在 −5.57 到 +5.57
   之间摆，写死任何一个值都错。

#### 采用的判据：残差的 **tile 聚集性**（与实现无关）

两种误差的空间结构完全不同：

| | 空间结构 |
|---|---|
| 截断偏置 | **均匀** —— 每个原子按自己的累加次数分摊，与位置无关 |
| 漏/重复 tile | **聚集** —— 按构造只影响某些 32 原子块，块内全中、块外为零 |

所以不看全体均值，看**按 32 原子块分组后的块内统计**：

    对每个 block b：  t_b = mean_b(ΔF·F̂_ref) / (std_b / √32)
    判据：max_b |t_b| 落在同精度 null 给出的分布内

截断偏置下 t_b 在各块之间同分布；漏一个 tile 会让某几个 t_b 成为极端离群值，
**哪怕全局均值完全正常**。这个判据不需要知道偏移量，也不随 kernel 设计漂移。

⚠ **必须在 OpenMM 的内部原子序上分块，不是用户序。** `CudaContext` 做空间重排，
返回给 Python 的力已映射回原序，连续的用户下标**不是**一个 tile，按用户序分块会把
信号抹平。C++ 侧用 `CudaContext::getAtomIndex()`；**因此这个测试必须写在插件的 C++
测试里，不能写在 Python 侧。**

逐分量判据保留（基线 ≈ 0，与实现无关）：`|t| < 3`。

#### 同精度 null 怎么造（不需要新 kernel，现在就能做）

需要一个"同算法、同精度、不同求和次序"的对照：

* **置换原子序**重建同一个体系，跑 CustomGBForce，把力换回原序再比。tile 组成完全
  变了、物理完全没变——顺带压的正是最担心的那条路径（排除对所在的 tile 结构变了）。
* 或 CUDA/single vs OpenCL/single，同样两侧 fp32。

两者都应给出全局 t ≈ 0（验证"两侧对消"），并给出 `t_b` 的 null 分布。**那才是本节该填
的基线。** 纯静态、零积分。

#### −5.57 不删，它有另一个用途

它是"fp32 相对 fp64 的截断签名"。kernel 出来后拿**新 kernel vs double** 再测一次：
若 t 与 −5.57 同量级，说明新 kernel 的累加次数与 CustomGBForce 相当；若显著更小，
说明融合生效、定点转换次数下降。**免费的实现自检**——能告诉你设计里那个"融合"有没有
真的发生，而不是只在文档里发生。

#### fixture（peer 的建议，采纳）

- **纯水盒子**：32 原子/tile ≈ 10.7 个水分子，**几乎每个 tile 都含排除对**，
  所以完全漏掉第一个循环会是灾难性的、一眼可见。
- **1AAY**：真正危险的是**部分错**（位掩码错一位、边界 tile 处理错），
  那才是"小力误差"的来源，也正是偏置判据的用武之地。

两个都留。`HIE149:ND1` 那条断言其实已经是偏置敏感的单点探针（它验的是"该没响应就
没响应"），本节是它的全体系版本。

## 4. cutoff 归属翻转单独立规则，不许混进统计阈值

DEC-004 记过：本 closure 的 pair 能量在 `rc` 归零但**力不归零**，残余
`k·qbase_i·qbase_j/rc³`，实测一次归属翻转值约 **29 kJ/mol/nm**。fp32 下落在 `rc` 附近
约 1e-7 相对范围内的 pair 算进算不进是掷硬币。

这类离散跳变**不是舍入**，把它塞进 rtol/atol 会逼着把阈值放宽两个量级，从而放过真正的
错误。规则：

1. 先按 `|r - rc| / rc < 1e-6` 标出边界 pair，从统计对照中**排除**。
2. 被排除的 pair **数量必须报告**。一帧里超过 `1e-6 × N_pairs × 10` 个就是异常
   （说明 cutoff 判据写错了，不是舍入）。
3. 对每个被排除的 pair，单独断言其力差落在"算进"或"算不进"两个合法分支之一
   —— 与 `test_fast_cutoff_roundoff_in_arbitrary_directions` 同一口径。

## 5. 性能验收

不是"越快越好"，是**必须报告 f 并对照 Amdahl 预期**：

- 在同一体系上跑 `profile_force_cost` 口径的对照：完整 CWLD（新 kernel） vs 去掉该力。
- 报告 `f = t_new / t_CustomGBForce` 和实际整体提速。
- **1AAY 实测 `s = 0.845`**（2026-09-03，`profile_force_cost`：完整 CWLD 63.06 ns/day
  vs 去掉 CustomGBForce 407.83 ns/day）。1CKK 是 0.811。两者差 3.4 个百分点，说明这是
  CustomGBForce 本身的代价结构，不是体系特异性的。
- f=0 天花板 **6.47×**（不是早先写的 12.5×——那个来自一个错误的下界推导，见 README）。
  **立项预期 2–3×**：f=1/3 → 2.29×（48.4 GPU 小时 → 21 h），f=1/5 → 3.09×（→ 16 h）。
- ⚠ **即使 kernel 免费也追不平 PME**：CWLD-minus-GB 是 407.83 ns/day，PME 约 663，
  仍慢 1.63×。原因是 cutoff 不同（PME 1.0 nm vs CWLD 的 rc 1.2 nm，直空间 pair 多 1.73×），
  与 CWLD 机制无关。验收时不要拿"追平 PME"当标准。
- ⚠ **瓶颈会转移**：那个 rc=1.2 nm 的 NonbondedForce 现在占 15.5%；kernel 快 5× 之后
  它会涨到约 48%。若实测整体只有 2× 左右，先确认瓶颈是不是已经转移过去了，再怀疑 kernel。

低于 1.5× 视为未达标，需要重新评估是否继续 100/110，而不是接受并宣布成功。

## 6. 不得事后修改本文件的阈值

kernel 跑出来偏差超标时，允许的动作是修 kernel、或写一份新的 DEC 说明为什么原阈值
在物理上不合理（并给出与实测结果无关的论证）。**不允许**把数字改成刚好能过。
本文件的任何修改都必须写明修改理由和日期。

### 规则会被绕过，理由不会

**判据只有在结果出来之前定下才算数；结果出来之后再改就是拟合。**

规则可以被绕过（"这不算改，这是澄清"），理由不会。所以判断一次修改是否正当，
不看它改了什么，看**改的时候有没有已知的结果**：

* 性能未达标线 1.5× 是在预期 2–3× 时定的。2026-09-03 的 rc 扫描把预期降到 1.6–1.9×，
  下沿离 1.5× 只剩 0.09×。**这个修改是正当的**——因为新 kernel 的性能还没测出来，
  论证只依赖 rc 标度这个独立事实。
* 同一个修改**在 kernel 跑分出来之后做就不正当**，哪怕论证一字不改。

所以待决项要在实测之前解决，不能拖到实测之后。决定权在用户。

## 追加（2026-09-04）：LCWLD-070 被跳过是有代价的，代价不在 CPU 性能上

070（Reference CPU kernel）当初以"不产生 ns/day"为由跳过。那个理由把 reference
kernel 当成了性能选项。它不是。

`LocalEnergyMinimizer` 在**含 LocalCWLDForce 的体系上跑不了**。路径：

```
LocalEnergyMinimizer::minimize
  -> ContextImpl::minimize                       ContextImpl.cpp
  -> CommonMinimizeKernel::execute -> lbfgs      CommonMinimizeKernel.cpp:383
       evaluateGpu(); if (!(fabs(energy) < FLT_MAX)) energy = evaluateCpu();  :386-389
                      同样的回退在线搜索里还有一处                             :430-438
  -> CommonMinimizeKernel::evaluateCpu                                        :572
        cpuPlatform = "CPU"，取不到则 "Reference"
        cpuContext = new Context(system, cpuIntegrator, *cpuPlatform);        :587
```

`system` 是**同一个** System，里面有 LocalCWLDForce；我们没有 Reference/CPU 实现，
于是抛 `Specified a Platform for a Context which does not support all required kernels`
—— 这条消息**既不说是哪个 kernel，也不说是哪个平台，更不说是次级 Context**。

触发条件是 **fp32 能量溢出**（起点或线搜索中途），所以它是间歇的：
本次 benchmark 里 `gb` 臂没触发、`new` 臂触发了，看起来像是我们的 kernel 挂了。
实际 `new` 臂的 Context 建得好好的，抛的是 `minimize`。

### 后果与处置

* **benchmark**：极小化改为只在 `gb` 臂上做一次，三臂共用结果坐标。
  这本来就该这么做 —— 每臂各自极小化会让三臂从不同坐标起跑，ns/day 不可比。
* **生产管线（重要）**：`lips` 走的是 `minimizeEnergy`。**LCWLD-080 落地、管线换成
  插件之后，第一次能量溢出就会硬失败**，而且报错信息完全指不到原因。
  在 080 之前必须先决定：补 070（一个只需正确、不需快的 Reference kernel），
  还是在管线侧改成"用 CustomGBForce 体系极小化、再换成插件体系跑动力学"。
  **070 不再是"跳过"，是"待定"。**
* 判据没有改动。本条只记机制，DEC-005 第 4 节的阈值一个没动。
